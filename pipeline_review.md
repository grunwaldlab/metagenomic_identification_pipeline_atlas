# Open-source shotgun metagenomic organism-identification pipelines

**Evidence checked:** 15 October 2026. This is a structured, source-linked review rather than a claim that a mathematically complete census of every unpublished or locally developed workflow exists. The search covered Europe PMC/PubMed and OpenAlex title/abstract searches for shotgun metagenomic pipelines, taxonomic classification, pathogen identification, viral metagenomics, microbial profiling, and metagenome assembly/binning; citation chasing from relevant reviews and benchmark papers; and direct examination of project documentation, source repositories, licenses, release histories, and resource pages. Repository and paper evidence is linked in the tables. “Not reported” means I found no defensible source value; it does not mean zero resource use or that a report cannot be assembled downstream.

Search discovery also used public GitHub repository searches for `metagenomic taxonomic pipeline shotgun`, `shotgun metagenomic pipeline organism identification`, and named hits/candidates (including EDGE, ATLAS, KAPTAIN, VirMake, MetaShot, RIEMS and SqueezeMeta). Screening was title/abstract and repository-led rather than a PRISMA-style exhaustive full-text review of every paper or repository hit; locally developed and unpublished pipelines may therefore be absent.

## Scope and screening rules

Included workflows must (1) accept untargeted shotgun DNA or RNA read data, (2) identify organisms without requiring the user to name a target organism in advance, (3) cover a broad community or a whole major taxonomic domain rather than a narrow genus/family, (4) have publicly accessible source code under a recognized open-source license, and (5) not require an account/API key to access an external web resource that is necessary for organism identification. Publicly downloadable reference databases are acceptable. Workflows that identify taxa only from assembled contigs/MAGs are retained but explicitly separated from direct read-classification workflows because their result semantics and costs differ.

“Capable taxa” means taxa the workflow can in principle report with its documented/default or user-supplied reference databases. It is not a guarantee of sensitivity, accuracy, or equivalent performance across taxa. Capability is database- and sample-dependent. A virus-focused workflow is eligible because it screens broadly for viruses without requiring a named virus. Host species used for host-read subtraction do not count as identified target organisms.

### Taxon coverage key

The matrix is a compact guide to *identification capability*, not an assertion that every taxon receives equal validation. **B** bacteria; **A** archaea; **V** viruses; **F** fungi; **P** plants; **An** animals; **Pr** protists and other microbial eukaryotes. `Y` = stated or a supported reference group; `DB` = possible when represented in a selected/user-built broad database, but not a promised/validated target; `~` = partial, optional, or limited; `—` = not a stated purpose and no useful documented basis for including it. For broad nucleotide/protein-database search pipelines, `DB` is intentionally cautious: sequence hits can exist outside the intended use, but that is not equivalent to a vetted taxonomic workflow.

## Grouping by identification strategy

### 1. Read-level k-mer / marker classification and abundance profiling

**nf-core/taxprofiler, bioBakery `wmgx`, MOCAT2, MGnify v5, HOME-BIO, MetaShot, KAPTAIN, and the optional Kraken module in MetaWRAP** belong here. These workflows classify reads directly, either by exact/approximate k-mer/reference matching (Kraken-family, Centrifuge, KMA) or by marker-gene mapping (MetaPhlAn, mOTUs, ribosomal markers). They are generally the most direct choice for community-level relative abundance profiles. Their principal trade-off is database dependence: taxon coverage and false positives change with database date/content and selected classifier. `taxprofiler` is the most configurable cross-classifier harness; `wmgx`, MOCAT2 and MGnify apply more curated microbial marker/reference strategies; KAPTAIN optimizes long-read reference classification and post-filtering. HOME-BIO and MetaShot combine domain-specific databases/classifiers. Sunbeam is a relevant unlicensed near-miss and is not in the qualifying set.

### 2. Broad clinical mNGS detection with candidate confirmation

**TaxTriage, local CZ ID/IDseq, EDGE, RIEMS and SURPI** focus on hypothesis-free detection in host-associated or surveillance samples. CZ ID, RIEMS and SURPI search broad nucleotide/protein references; IDseq adds host subtraction, assembly and contig-refined alignments. TaxTriage adds candidate alignment, ambiguity handling, evidence scoring and an investigative report. EDGE assembles multiple standard analyses and report modules. These pipelines are better aligned to pathogen discovery than census of a microbial community, but broad reference search increases compute/storage needs and low-abundance hits require review. Hosted account-based products are not interchangeable with qualifying local code paths.

### 3. Assembly, homology, and genome-resolved identification

**SqueezeMeta, nf-core/mag, ATLAS, IMP, Metagenomics-Toolkit, and MetaWRAP's principal workflow** assemble reads, identify genes/contigs/bins, then assign taxonomy by homology, reference mapping or genome placement (e.g. DIAMOND/BLAST, CAT/GTDB-Tk). They can recover genome context and provide more coherent evidence for an organism, but may fail to identify low-abundance taxa that do not assemble and can require substantial intermediate disk. Taxonomic calls are often attached to genes, contigs or MAGs, not equivalent to read-level relative abundance tables. nf-core/mag and MetaWRAP also include read-classification stages/modules, but their overall purpose is genome recovery.

### 4. Virus-domain pipelines

**ViroProfiler, nf-core/viralmetagenome, VirMake, and metavirs** restrict the intended search to the viral domain while remaining untargeted among viruses. Their common pattern is viral read QC/background filtering, de novo assembly, viral sequence recognition, and taxonomy/annotation. They are appropriate where virus recovery and characterization is the objective; they do not replace bacterial/archaeal/fungal community profiling. VIRify is a strong related viral contig classifier but is not in the qualifying set because it accepts assemblies rather than raw shotgun reads.

## Interpretation and practical conclusions

1. There is no single “best” workflow independent of objective. For community abundance profiling, compare marker/k-mer profilers on a fixed, recorded database. For pathogen discovery, use host subtraction and independent evidence review rather than accepting every low-abundance taxon call. For genome recovery, use assembly/MAG workflows and expect different detection limits and much larger intermediate storage.
2. “Taxa capable of identifying” is primarily a property of the selected database and the included classifier. The same pipeline can be narrow (custom bacteria-only reference) or broad (all-organism nt/nr); report the exact database build/date and taxonomy snapshot for any real comparison.
3. Viruses, fungi, protists, plants and animals are poorly represented in some general microbial marker databases. A `DB` in the matrix means only that configured references can produce a hit, not that the pipeline was validated for that group.
4. Several older workflows meet the technical scope but have obsolete dependencies, taxonomic identifiers, or database snapshots (SURPI, RIEMS, MOCAT2, MetaShot, HOME-BIO, MGnify v5, ATLAS, MetaWRAP, metavirs). “Open source” should not be mistaken for currently installable or maintained.
5. The resource comparison is a significant evidence gap. The available figures mostly describe machine provisioning, reference downloads, or one study's wall-clock time. A defensible benchmark should report FASTQ read count/base count and read length, host fraction, database snapshot and bytes, full hardware/cores, per-process peak RSS, measured CPU time, wall time, output/intermediate bytes, and whether database build/indexing is included. Report results separately by tool/database and taxonomic class only when the benchmark was designed to support that comparison.
